# Render deployment

The repository includes `render.yaml` for a same-region deployment consisting of:

- a free Static Site for `frontend/`;
- a free gateway Web Service;
- a paid Private Service for the provider simulator;
- three paid Background Workers, one for each recovery workflow; and
- a same-region Render Postgres database.

The provider simulator is intentionally private. The gateway and workers use
`http://payment-provider:3001` over Render's private network, while the browser
uses the gateway's public URL through `VITE_API_BASE_URL`.

## Required values during Blueprint setup

Render prompts for the values marked `sync: false`:

- `CORS_ORIGIN`: the deployed Static Site URL, for example
  `https://payment-reliability-playground.onrender.com`;
- `VITE_API_BASE_URL`: the gateway Web Service URL, for example
  `https://payment-gateway-api.onrender.com`.

`WEBHOOK_SECRET` is generated by Render and shared with the gateway only. Do
not put database credentials or webhook secrets in the repository or in
`VITE_*` variables.

## Deployment order and commands

The gateway's start command runs `npm run migrate:latest` before `npm start`.
This keeps the gateway on Render's Free Web Service plan; use a single gateway
instance when relying on this startup migration pattern. The database URL is
supplied by Render's internal Postgres connection string. Each worker also
runs the same migration command before starting; Knex's migration lock keeps
concurrent startup migrations serialized. The provider builds with
`npm run build:provider` because
the provider lives outside the root TypeScript `src/` compilation. The three
workers build with the root `npm run build` and run their compiled entrypoints.

After deployment, verify:

```text
GET https://<gateway>.onrender.com/health
GET https://<gateway>.onrender.com/metrics
GET http://payment-provider:3001/health  # from a Render service shell only
```

Create a payment in the frontend, repeat the request with the same idempotency
key, then reuse that key with a changed payload to demonstrate the conflict
response. The provider simulator is in-memory, so provider records disappear
when that service restarts; this is a deliberate demo limitation and not a
durable production-provider substitute.

## Cost and operating limitations

Static Sites are free. Free Web Services and Free Postgres are available for
testing, but Free Postgres expires after 30 days and has no backups. Render
does not offer Free plans for Private Services or Background Workers, so the
complete architecture requires one paid provider service and three paid worker
services. The Blueprint uses the smallest current paid compute plan for these
services.

The three workers are kept as separate processes so each workflow has
independent shutdown, lease recovery and failure isolation. Combining them
would require a new supervised launcher and would reduce cost at the expense
of isolation; it is not silently enabled by this Blueprint.

For a lower-cost demo, run only the gateway, provider and database and omit
the workers. Client requests and webhooks still work, but automatic uncertain
payment, provider-conflict and orphan recovery will not run until the workers
are deployed.
